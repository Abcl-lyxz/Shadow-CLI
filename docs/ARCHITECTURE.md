# Architecture

## Boundaries

The Go host process owns the TUI, provider HTTP connections, persistent state, Docker control, target policy, and loopback dashboard. It does not run model-generated shell commands. The sandbox image owns security executables and runs with a separate scratch directory and read-only user mounts. A host-side HTTP gateway can query explicitly allowed local fixture URLs; only package-local tests expose its recorded read path to a model tool. The shipped UI offers no network action grants. General-purpose tools need complete side-effect and evidence policy before receiving live network access; container networking remains disabled.

The event log is the durable source of truth for the current development slice. Fixture HTTP responses are stored as minimized observation events plus AES-GCM encrypted raw evidence. The evidence key lives in the OS keyring, outside SQLite. Startup checks SQLite and every evidence pair, then verifies an HMAC-linked append-only active-state ledger and separately held head before permitting writes. Event/evidence transactions make the ledger entry durable before SQLite commit; an interrupted commit fails closed and requires recovery. The ledger and head are outside the SQLite directory by default. First enrollment cannot attest earlier history, and a whole-profile rollback requires an independently held copy of the head to detect. Cross-process provenance locking and stronger backup custody remain release work.

The TUI performs a bounded 90-day age-based prune at startup after integrity checks; the operator may set 1-365 days. The existing manual plan/prune commands remain. Unresolved cleanup obligations and active fixture request leases block deletion. Purge appends a new provenance state, while old ledger entries keep only digests. Encrypted recovery bundles use an in-memory SQLite image capped at 128 MiB. Restore verifies the archive anchor, authenticated chunks, SQLite integrity, and evidence before installing the recovered key and creating a previously absent database. A fresh location starts a new provenance baseline; it does not erase the source chain. Backups, keys, anchors, provenance, and storage remnants are outside active-run retention.

Untrusted Docker stdout/stderr and model-authored memory summaries are withheld from agent context and events; runtime exit code and output byte count remain. Free-form model answers are shown in the local TUI, while event storage withholds their text. Dashboard event payloads and finding title/asset fields are withheld, including old rows. Typed fixture observations remain available without raw URL, headers, or body; MIME metadata is restricted to six known values. This intentionally limits the development agent's shell analysis until a trusted typed extraction path exists. See `docs/DATA_LIFECYCLE.md` for custody, restore, and residual limitations.

Finding records link to an evidence-backed observation in the same run. Creation writes a durable event in the same transaction so a later recorded fixture GET can be ordered by event ID; older findings retain the prior timestamp check. An exact response reproduction can mark only a response-observation claim verified when URL hash, status, and complete body hash match. Security hypotheses cannot be upgraded by this response-match path. The dashboard displays status and source event IDs without decrypting raw evidence.

The local review layer appends a `finding_reviewed` event with bounded PoC status, confidence, same-run duplicate link, and an optional explicit CVSS v4 vector/score. It does not change a security hypothesis into a verified vulnerability. `internal/report` reads authenticated evidence and the current review, then produces a canonical document whose digest an operator must confirm before export. An optional 64 KiB operator-authored sidecar supplies narrative and metric rationale for that document; model text and stored free-form finding titles are not copied into reports. Known secret patterns are refused, while the human still must inspect the full preview. The dashboard exposes only review metadata. Narrative sidecars are not stored in SQLite. An isolated manual public-target read can create only a response observation from already saved GET evidence, then use the same review/export path without another network request.

The preparatory action policy classifies exact URL and method pairs declared by trusted runtime code; unknown actions fail closed. A named test write requires a cleanup route before it can be journaled. The store records the plan, possible dispatch, cleanup attempt, and later authenticated same-run observation without raw URLs in the event log. The journal alone does not execute requests or prove cleanup succeeded. Fixture-only dispatchers can create a fixed named marker and inspect or remove it; they remain separate from agent tools, and the Docker network stays disabled.

A bounded versioned JSON document can declare operator-authored action rules for one already selected exact origin. Parsing rejects duplicate/unknown fields and unsafe or incomplete action contracts. `shadow policy validate` is read-only. Fixture tests pass parsed rules into the immutable run snapshot and exercise scope escape and unknown mutation outcomes. The shipped UI does not load this document or grant live network actions. Generic target semantics and policy provenance remain release gates.

The internal fixture dispatcher applies trusted GET/read rules, derives its own exact URL list, and requires a loopback destination. It binds to one immutable run scope/action snapshot; every supplied rule must match a stored grant. It rechecks that snapshot before each request and redirect hop, then checks the run identity and final read grant inside the encrypted-evidence transaction. A purged or reused run cannot receive evidence from a stale fixture response. Recorded reads require an evidence key before dispatch. Each run also has a durable fixture request budget: 16 ordinary HTTP hops and four reserved cleanup hops, one in-flight lease, and a shared minimum interval across dispatcher instances and restarts. The lease blocks purge or age-based prune while a request is active; a crash leaves the spent request charged and the lease expires after 30 seconds. Runs created before the budget table fail closed for fixture requests. The lease ends when the HTTP hop completes, so a later purge before evidence recording is still handled by the evidence transaction's snapshot check. Exhausting cleanup capacity leaves an obligation for review; this is not a guarantee that cleanup can always be completed. The raw HTTP fetcher and unrecorded read are package-private; the old unbound `Fetcher.GetRecorded` path was removed. Authentication and test-write classifications are denied at read dispatch. A new run atomically stores an immutable origin/action snapshot, budget, and start event; the action snapshot contains route hashes rather than raw paths or queries. Test-write planning requires an exact grant in that run's snapshot, and legacy runs without snapshots cannot gain write permissions. The CLI can show the snapshot and journal metadata, then record a human review against one current state event. Review never clears an obligation or proves resource removal.

Package-local agent fixture tests can install exact GET/read rules before starting a run. Only then is `fixture_http_read` offered to the fake provider. The model sees action IDs instead of raw rule URLs and must select one ID; the run-bound dispatcher resolves it to a trusted rule and rechecks the immutable snapshot. Each HTTP hop records a `network_decision` event before dispatch with method, URL hash, and policy result. Direct unlisted requests and rejected cross-origin redirects also record hashed denials. The event records policy authorization, not proof that a request was sent or that the endpoint had no side effect. The response tool result contains event ID, status, size, and hashes rather than raw headers, URL path/query, or body. A default UI run still starts with no network grants and advertises no network tool; forged calls fail at runtime. This test path cannot reach public targets or send writes, and is not a production network API.

`FixtureRunNetwork` gives trusted local code typed entry points for recorded GET, fixed fixture marker/record POST, cleanup DELETE, read-only recovery inspection, and loopback authentication. The raw fetcher, URL allowlist, read/write dispatchers, and cleanup executor are package-private; external broker callers can construct only typed run-bound gateways. It derives action IDs from run-bound trusted rules; a caller-provided URL list cannot add a destination. Authentication resolves a run/origin/action/creation-bound credential reference from a separate OS-keyring service only at dispatch. A fixed JSON POST may establish one volatile session from an exact HTTP 204 response and a bounded host-only cookie. Authenticated reads attach that cookie only to granted GET actions at the same pinned loopback destination; redirects are refused and a restart has no session. Authentication responses are not persisted, and decisions contain only URL hashes. For permitted fixture POST and cleanup DELETE, the store checks the exact run grant and current journal state in the decision transaction before the fetcher reserves a durable HTTP hop. Denied mutation attempts are also recorded by URL hash when a dispatcher can identify its run. This local API is still fixture-specific: its SQLite decision log is not independently tamper-resistant, and it supplies no public-target access or general side-effect contract.

The local operator can sign a normalized trusted rule digest with a distinct OS-keyring HMAC key. `StartApprovedRun` atomically binds the verified approval ID, rule digest, and expiry to the run start event and an immutable approval row. `ApprovedReadNetwork` is a read-only gateway for such runs. It rejects non-GET effects, missing evidence keys, expired or changed approvals, and private/loopback destinations in its public constructor; every hop rechecks the snapshot and approval, records a hashed decision, consumes the durable run budget, and stores only encrypted raw evidence plus minimized metadata. Controlled loopback tests and one explicitly authorized public homepage read exercise this path. The manual `shadow target read` CLI runs one approved action in a dedicated data directory; the agent and TUI cannot construct this gateway. Production evidence review, authentication/write contracts, and the full controlled-target negative suite remain open.

The internal fixture cleanup executor handles an already journaled possible write at one loopback origin. Trusted run grants must include the named write and a GET of its exact cleanup URL. A recorded GET must show the named marker present after the possible write. The executor commits `cleanup_attempted` before sending an exact DELETE, rejects DELETE redirects, then records an encrypted GET response. Only the local fixture JSON contract (same resource present with HTTP 200, then absent with HTTP 404) can advance the journal to `fixture_cleanup_verified`. Failed, cancelled, or interrupted requests leave an obligation for review; the executor does not replay them. This is not a generic cleanup strategy, proof of a live target action, or an agent tool. Container networking remains disabled.

The internal fixture write dispatcher requires an immutable run grant for an exact POST marker route and a GET of its cleanup URL. It first records a GET proving the marker absent, reserves that marker across runs at the same origin, commits `write_may_have_happened`, and sends only a runtime-generated JSON marker body. It rejects POST redirects and records a later encrypted GET to prove presence; failures leave an unresolved journal obligation. After restart, the cleanup executor can inspect a possible write with GET, or inspect an interrupted DELETE with GET and verify the fixture's absent-marker contract without replaying a mutation. Per-run purge rejects unresolved test-write states, including an in-flight mutation after its possible-write state is committed. This remains an internal loopback contract; generic target semantics and production evidence handling are open release gates.

The broker has two local semantic cleanup protocols with present, absent, and unknown outcomes. `fixture_marker_v1` checks HTTP 200/404 marker JSON; `fixture_record_v1` checks exact active/deleted record JSON with HTTP 200/410 and fixed record routes. New fixture plans persist the selected protocol; an untyped generic plan cannot authorize POST or DELETE. Older journal rows marked `legacy_untyped` can finish only through the full marker absence proof when their run snapshot and evidence are available, and cannot replay a write. An unresolved observation can be reinspected with a fresh encrypted GET after restart without replaying a mutation. `docs/NETWORK_CONTRACT.md` defines the session and cleanup limits. Action policy rejects URL userinfo and authentication URLs with queries so credentials cannot be placed in those trusted rule fields.

## Product modules

The local agent orchestrator creates a no-network-grant run and seals a four-role plan (`surface` and `source` in parallel, then `verify`, then `report`). Each role has a runtime tool allowlist and a separate bound on model steps, input/output tokens, priced cost, context bytes, and tool calls. The OpenAI-compatible adapter asks for a bounded output and requires reported usage before any returned tool call is executed. The catalog or operator supplies the price used for the cost estimate; actual provider billing must still be reconciled. Verified shared memory contains only independently reproduced HTTP response metadata and same-scope evidence IDs, with a fixed `reproduced_response` confidence and 30-day expiry. It cannot turn a response match into a verified vulnerability. Untrusted free-form notes and prior agent answers remain withheld from shared context.

Plan snapshots contain a prompt digest, secret-free route, budget, and roles; an event seal detects changed route/budget metadata. Jobs commit metadata-only checkpoints before provider dispatch, after usage, before each tool, and after tool return. Restart recovery marks any `running` job `interrupted` with an unknown outcome and never resends a tool automatically. An operator must review possible effects before explicitly returning that job to `pending`; the original task text and same route are required to continue. Pending and unknown-outcome jobs block retention/purge. These local operations do not grant agents public-target network access. Cross-process writer coordination and actual provider billing checks remain release work.

1. Provider catalog and protocol adapters resolve an active route and confirm model capability.
2. Orchestrator schedules bounded agent tasks with budgets and cancellation.
3. Policy validates target scope and actions before any side effect.
4. Sandbox manager creates restricted Linux containers via Docker.
5. Store holds runs, events, memories, findings, and evidence metadata.
6. TUI and loopback dashboard consume the same application state.

## Interfaces

The default CLI entry point is `shadow`. Implemented scriptable commands include `shadow doctor`, `shadow sandbox run`, `shadow tools audit`, `shadow data review-finding`, and local `shadow report preview/export`. TUI slash commands are versioned with the app. Browser APIs are local and versioned under `/api/v1`.

Provider names and models come from Models.dev plus endpoint discovery. Transport adapters are protocol-specific; a new provider that speaks a supported protocol needs no provider-specific source change. The chosen route must be the route used for inference, including after a TUI change.

## Delivery decisions

The first release is single-user and local. Web/API requests can be tested dynamically. APK, IPA, PE, Mach-O, and ELF analysis is static unless execution is possible inside the Linux sandbox. There is no claim of Windows/macOS/iOS GUI execution.

The local artifact inspector reads one bounded regular file from an operator
path or a TUI attachment, hashes it, and parses container or executable
metadata without extraction or execution. TUI paths are resolved and checked
inside the attached root. The signed passive plugin API accepts only
`static-magic-v1` byte patterns over a 4096-byte prefix under an explicitly
supplied Ed25519 trust key. Its output is an operator-visible label, not
evidence of a vulnerability. It has no executable, provider, or network
capability. See `docs/STATIC_ARTIFACTS.md`.
